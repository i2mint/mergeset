Real vitest output from two *semantic* conflicts, captured by the TEST workstream. Both are cases where every change is green alone and the pair fails, so they exercise the "map failing tests → files → the branches that touched them" path rather than any textual signal.

- `vitest-579-631-drift.txt` — `{#579, #631}`. The failing ids are `tests/unit/params-ssot.test.ts > generated AI artifacts > ai/schemas/'…' matches the TypeScript sources`. Note what attribution has to do here: the failing test lives in a file **#631** added, but the change that broke it is **#579**, and #579 touches none of #631's files. The diff body names the culprits directly (`pointColorHopDirection`, `pointColorHopSeeds`, `hopDistance`, `TraversalDirectionType`), which is the strongest signal available — a symbol-level match against each branch's diff finds #579 in one step, whereas file-level attribution points at #631 and is wrong.
- `vitest-577-587-import-crash.txt` — `{#577, #587}`. Four files fail to *collect*, not to assert, so there are no per-test ids at all — vitest prints `FAIL <file> [ <file> ]` plus one shared stack trace. The actionable line is `packages/app/features/project-builder/store/commands/schemas.ts:89`, which is a **source** file (added by #577), not a test file. Any parser that only harvests test ids gets nothing useful from this; the file path in the stack frame is what identifies the branch.

Together they argue for: (1) parse both the `FAIL <file>` collection form and the `FAIL <suite> > <case>` assertion form; (2) attribute via *all* paths mentioned in the failure block, source files included, not just the failing test's own path; (3) when a failure block names identifiers, match them against the candidate diffs — it is the only signal that gets `{#579, #631}` right.
