mergeset.validation#

Validation functions: does this merged tree actually work?

A validator is any callable (worktree_path) -> ValidationOutcome. Four are shipped — a pytest runner (the default), an arbitrary shell command, a local CI run via act, and “merge-only” — and a user-supplied Python callable is a first-class fifth option, because the interesting projects always have one more step than a test command.

Every validator returns a structured result, not a bit: which tests failed, which files they live in, how long it took. The solver uses that to aim its conflict shrinking at the changes actually implicated, rather than halving blindly.

A validator may also say what it runs: a validator_fingerprint attribute, a short digest of its command, stages, timeout and environment. Every shipped validator carries one, and the evaluation log stamps it on each row, so a row recorded by pytest -x never answers a question asked of pytest -m e2e (i2mint/mergeset#32). A user callable has none unless it sets one, since only its author knows what changes its verdicts: my_validator.validator_fingerprint = 'smoke-v2'. Its rows are stamped UNKNOWN_FINGERPRINT, which matches only other such rows. A wrapper made with functools.wraps copies the wrapped validator’s fingerprint along with its __dict__; a wrapper that changes what is checked must set its own.

A fingerprint covers the command’s text. When the command runs a script that lives outside the analysed repository (python ~/checks/smoke.py), the script’s contents are not in it: files inside the repository are pinned by the commits, files outside it are not. Name such files with inputs= and their contents join the fingerprint, so editing the script retires the verdicts it gave (i2mint/mergeset#39).

Content digests of input files, keyed by the file’s path and stat (#42). Reading an 8.5 GB tree takes about a minute; stat-ing it, seconds. A run digests its inputs once per validator built and twice around every evaluation, so all but the first read come from here.

mergeset.validation.RACY_SECONDS = 2.0#

How old a file’s last change must be before its stat may vouch for its contents. An edit within one timestamp tick of a read leaves size and mtime as they were (git’s “racy clean” problem); 2 s covers the coarsest common filesystem timestamps (FAT). Younger files are always read.

class mergeset.validation.ValidationStage(name, command, fingerprint=None, timeout=None, required=True)[source]#

Bases: object

One step of a staged validation.

Parameters:

  • name (str) – What this step is (setup, build, test, lint…). It ends up in the log and in the report, which is the whole point: “failed to build” and “tests failed” are different facts and a single pass/fail bit throws away the one you need.

  • command (str) – Shell command, run in the merged worktree.

  • fingerprint (Optional[Callable[[str], str]]) – Optional worktree -> str. When given, the stage is skipped if it already ran in this worktree with the same value — this is how an expensive dependency install is amortized across evaluations instead of being paid every time (keyed on, say, the hash of the lockfile).

  • timeout (Optional[float]) – Seconds before the stage is declared failed.

  • required (bool) – A failing required stage fails the whole validation and stops the sequence (the default). A non-required stage’s failure is recorded in failing_tests and the set still counts as good — for an advisory pass, such as a lint the project runs as a separate CI job rather than a gate.

Ordering matters more than it looks. mergeset.validation.fingerprint_of(validate)[source]#

What validate runs, as a short string – or None when it cannot say.

Two validators with the same fingerprint give the same verdict on the same tree, so an evaluation log may answer one with the other’s rows. None means unknown: such a validator’s rows are recorded as UNKNOWN_FINGERPRINT (see recorded_fingerprint()), and answer only other validators that cannot say what they run either.

mergeset.validation.inputs_digest(paths, *, cache=FILE_DIGESTS)[source]#

A digest of each path’s current contents, keyed by its real path.

These are the files a validator runs that its command text does not capture: a script outside the analysed repository, a config it reads. A directory is digested over every file under it (names and contents, following symlinks, each directory once; __pycache__, *.pyc and dot-directories such as .git are left out, since running the inputs writes them), a missing path as 'missing' – so creating it later changes the digest too – and one that cannot be read as 'unreadable'. Relative paths are resolved against the current directory, not the worktree: files inside the repository are already pinned by the commits. paths is a collection of paths: a lone string is refused, since it would be read one character at a time.

A file whose path, inode, size, mtime and ctime match an earlier read is not read again: its digest comes from cache (default FILE_DIGESTS), but only once its last change (mtime or ctime, which no tool can set back) is RACY_SECONDS older than that read. cache=None reads every file.

Trusting a stat is what make and git do, with their blind spots: a second write through a shared mmap to an already-dirty page changes no timestamp, and a network filesystem may serve cached attributes (NFS, for up to a minute) or stamp times from a clock behind this one. For inputs edited that way, pass cache=None, or set mergeset.validation.FILE_DIGESTS = None to turn the cache off for every validator (ADR 0035).

Return type:

Dict[str, str]

>>> import tempfile
>>> with tempfile.NamedTemporaryFile('w', suffix='.py', delete=False) as f:
...     _ = f.write('print(1)')
>>> before = inputs_digest([f.name])
>>> with open(f.name, 'w') as g:
...     _ = g.write('print(2)')
>>> inputs_digest([f.name]) == before
False
>>> os.remove(f.name)
>>> list(inputs_digest([f.name]).values())
['missing']

mergeset.validation.staged_validation(stages, *, env=None, inputs=())[source]#

Run an ordered list of ValidationStage steps, reporting which one failed.

Real projects do not have “the test command”; they have a sequence, and the steps are not equally interesting. A JS repo may need pnpm install (slow, only when the lockfile moved), then a build (a prerequisite of testing — without it the tests do not even collect, and a validator that skipped it would report a false failure), then the tests, then a lint pass.

The failing stage’s name is prefixed onto every reported failure id, so the log distinguishes build: ... from test: tests/x.ts::y.

inputs names files outside the repository that any stage runs; their contents join the fingerprint (see inputs_digest()).

Return type:

Callable[[str], ValidationOutcome]
