mergeset#

Which of these branches can be merged together?

Given a base commit and n candidate changes (branches, PRs, commits), mergeset finds the maximal sets that merge cleanly and still pass validation — and the minimal conflicts that stop the rest.

The simple case is one call:

from mergeset import analyze, branch_changes, markdown_report

changes = list(branch_changes('.', ['feature-a', 'feature-b'], base='main'))
analysis = analyze('.', changes)
print(markdown_report(analysis))

Everything expensive is cached in an append-only JSONL log, so a second run costs nothing for sets already decided, and the cheap oracles (per-change CI status, git merge-tree textual conflicts, file-overlap decomposition) run first so that most answers never cost a test run at all.

Every piece is one keyword argument away from being replaced: where changes come from (mergeset.sources), how a set is merged and validated (mergeset.oracle, mergeset.validation), how the search spends its budget (mergeset.solve), how results are rendered (mergeset.report), and where artifacts are kept (mergeset.storage).

Everything mergeset produces — reports, evaluation logs, captured validation output, fixtures — is derived from whatever repository was analysed, so it goes to an artifact store rooted at ~/.local/share/mergeset/<kind>/ and never into a repository. Point that store at S3 with one keyword argument; no caller changes.

property evaluations: int#

How many expensive evaluations this analysis rests on.

In a tiered run, those of the first tier (log); every tier’s count is evaluations_by_tier, which is what the reports show.

Counted from the log, which is the source of truth, not from the search state, which only knows what this process ran. Regenerating a report from a complete log spends nothing, and the search-state number then reads 0 — so the better the cache worked, the more the archived report understated the work. A real 18-candidate run that cost 9 evaluations and 344 s reported “0 expensive evaluations spent”.

Rows are counted when they decided something about this candidate set: a recorded PASS or FAIL (an ERROR established nothing) over a subset of the changes in play (so an older run’s rows for a different candidate set in the same log are not claimed as this analysis’s work). The base check counts — it is an evaluation, and on a real project it is one of the slowest.

class mergeset.AnytimeAnswer(best, best_weight, best_tier, full_depth, bound, bound_set, gap, optimal, pending=(), spent=<factory>)[source]#

Bases: object

The best answer so far, and how much better an answer could still be.

bound is a genuine upper bound, not a hope. Every conflict — found at any tier, by any pre-oracle — refutes a real set, so the heaviest set that no known conflict forbids is the heaviest set that could still pass. Its weight is therefore an upper bound on the optimum, and gap is what is still unknown.

gap <= 0 together with full tier depth is a certificate: the heaviest set nothing refutes has itself been validated, so nothing better exists. That is a stopping rule rather than a budget running out.

Heaviest set validated so far, at best_tier.

best_weight#

Its weight (the sum of its changes’ weights).

best_tier#

Deepest tier that actually ran on best; None when nothing has been validated yet.

full_depth#

True iff every tier ran on best. When False, best is a partial claim however good gap looks.

bound, bound_set

The upper bound and the set that realizes it.

gap#

bound - best_weight — what might still be being missed.

optimal#

pending#

(set, estimated seconds to confirm) for candidates not yet taken to full depth. The answer to “what would closing the gap cost”.

class mergeset.Evaluation(subset, verdict, stage=None, merge=None, validation=None, duration=0.0, at=None, note='', base_sha=None, heads=<factory>, validator=None, resolver=None, cached=False)[source]#

Bases: object

One row of the evaluation log — the single source of truth.

Everything else (conflict set, known-good/known-bad closure, merge plan, reports) is derived from a sequence of these and is re-derivable.

A row is about the commits that were actually merged, not about the ids: base_sha and heads (change id -> head sha) pin it to them, so a row written before a branch was rewritten is never mistaken for an answer about the rewritten branch (i2mint/mergeset#23). Rows written before pinning existed carry neither and read back as unpinned; see mergeset.log.EvaluationLog. validator pins it to what was run on that tree, the same way (i2mint/mergeset#32): the same commits under a different test command are a different question.

Full sha of the base the set was merged onto. None on unpinned rows.

cached: bool = False#

True when this came from the log rather than from a real run. Not serialized: it is a fact about this lookup, not about the evaluation.

class mergeset.EvaluationLog(store=None, *, pins=None, trust_unpinned=False)[source]#

Bases: object

Append-only record of evaluations, plus the monotone closure over it.

Parameters:

  • store (Any) – Persistence seam. A path (str/PathLike) is wrapped in JsonlLines; pass StoreLines to put the log in an artifact store (S3 and friends), or MemoryLines for an ephemeral log. With no argument at all the log goes to the artifact store’s evaluations/adhoc.jsonl — never the working directory.

  • pins (Optional[Pins]) – The commits the questions are about (see Pins and pin()). Unpinned, every row counts, as before pinning existed; mergeset.analyze() always pins.

  • trust_unpinned (bool) – Let rows that record no commits at all (written before i2mint/mergeset#23, or by an unpinned log), or no validator while the pins name one (written before i2mint/mergeset#32), count as matches once the log is pinned. Off by default, because such a row may be about a head that has since moved, or judged by a command that has since changed — which is the defect pinning exists to close. Turn it on only when you know neither has changed since those rows were written; it is the migration path for an old log. A row whose recorded commits or validator differ never counts.

mergeset.inputs_digest(paths, *, cache=<object object>)[source]#

A digest of each path’s current contents, keyed by its real path.

These are the files a validator runs that its command text does not capture: a script outside the analysed repository, a config it reads. A directory is digested over every file under it (names and contents, following symlinks, each directory once; __pycache__, *.pyc and dot-directories such as .git are left out, since running the inputs writes them), a missing path as 'missing' – so creating it later changes the digest too – and one that cannot be read as 'unreadable'. Relative paths are resolved against the current directory, not the worktree: files inside the repository are already pinned by the commits. paths is a collection of paths: a lone string is refused, since it would be read one character at a time.

A file whose path, inode, size, mtime and ctime match an earlier read is not read again: its digest comes from cache (default FILE_DIGESTS), but only once its last change (mtime or ctime, which no tool can set back) is RACY_SECONDS older than that read. cache=None reads every file.

Trusting a stat is what make and git do, with their blind spots: a second write through a shared mmap to an already-dirty page changes no timestamp, and a network filesystem may serve cached attributes (NFS, for up to a minute) or stamp times from a clock behind this one. mergeset.slash_separated_keys(store, *, sep='/')[source]#

Make / the key separator whatever the platform’s is.

Keys are a store’s public namespace, so they must not change shape with the operating system: a report written under 'run-a/REPORT.md' has to read back under that key on Windows too, and an S3 backend uses / regardless. Without this the same key is two different keys on two machines — the filesystem leaking through the abstraction the store exists to provide.

A no-op where the separator is already /.

Return type:

MutableMapping

>>> store = slash_separated_keys({}, sep='/')
>>> store['a/b'] = 1; dict(store)
{'a/b': 1}

On a backslash platform the backing store sees native separators while callers keep using /:

>>> backing = {}
>>> store = slash_separated_keys(backing, sep='\\')
>>> store['a/b'] = 1
>>> list(backing)
['a\\b']
>>> list(store), store['a/b']
(['a/b'], 1)

mergeset.textual_conflict(repo, base, head_a, head_b)[source]#

Conflicting files if merging both heads onto base clashes textually.

**This chains through base on purpose.** Plain git merge-tree A B merges using merge-base(A, B), which is not base whenever the two branches were cut at different times — and then it reports base’s own commits as conflicts. On a real 15-PR set that mistake produced 13 “conflicting” pairs where only 2 were real (measured by TEST on a real trial). So we merge A onto base first, in the object database, and ask whether B then conflicts with that.

Optional[List[str]]

None when the merge is clean, otherwise the list of conflicted paths (possibly empty if git reported a conflict it could not attribute).
